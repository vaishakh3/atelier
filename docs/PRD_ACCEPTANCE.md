# PRD acceptance and remaining release gates

This matrix traces `AI_BIM_MVP_PRD.docx` to the current standalone desktop implementation. “Implemented” means code exists for the stated bounded workflow, with the listed automated evidence. It does not mean professional acceptance, certification, or completion of the PRD's design-partner pilot. Final packaged GUI results belong in [VALIDATION.md](VALIDATION.md).

The authoring scope remains low-rise architectural BIM: rectangular walls/slabs/rooms, rectangular hosted openings, flat roofs and regular straight stairs. Structural analysis, detailed MEP design, freeform geometry, fabrication-grade documents, automatic permits and regulatory sign-off remain outside the PRD scope.

## Functional requirements

| PRD requirement | Implemented behaviour | Automated evidence | Remaining acceptance or limitation |
|---|---|---|---|
| **FR-01 Project foundation & persistence — P0** | Projects, levels, grids, canonical metre geometry, display units, queued autosave, undo/redo and immutable snapshots. Desktop records and per-user recovery drafts are encrypted. Atomic replacement, authenticated recovery generations and `If-Match` reject stale writes. Restoration creates a new revision with server-attributed audit. | `startup`, `transactions`, `storage` and `server-auth` suites cover restart selection, transaction boundaries, recovery, concurrent writers, audit and access isolation. The final macOS package retained 43 elements/v4 after repeated save and restart; native backup restore created a separate 43-element/v3 project without changing the original. | Native crash/migration drills and a professional backup/retention policy with operational ownership must be agreed with the pilot firms. |
| **FR-02 Core geometry editor — P0** | Supported element authoring, dimensions/snapping, property/type edits and coordinated plan/section/elevation/3D data. Model validation links invalid hosts, bounds and overlaps to element IDs. Rendering and quantity calculation share the clipped union of hosted openings. Bounded repetition copies walls with their children. A room-program generator proposes a single-storey rectangular concept with connected circulation, attached bathrooms, shared walls and hosted openings on an empty level or a selected empty slab. | `geometry`, `drawings`, `engine` and `repetition` suites cover rotated coordinates, openings, union deductions, views, annotation provenance, dimensions and detached copies. | This is a bounded rectangular representation, not a general CAD kernel. Independently review supported architectural details and agree quantity tolerances. Complex roofs and stairs are reference-only or excluded. |
| **FR-03 IFC interoperability — P0** | IFC2X3/IFC4-family STEP subset import and IFC4 export; supported geometry, IDs, primitive properties, nested placements, selected type/material inheritance and unit conversion. Per-class editable/reference/excluded counts and source-unit metadata. Safe bounding proxies remain read-only. | `ifc` round-trip/invalid-file tests and `ifc-external` tests against three pinned, unmodified buildingSMART IFC4X3_ADD2 examples. Fixture bytes and provenance are checked independently of the application exporter. | Three compact external examples do not form a representative office/vendor/MVD corpus or certification. Mapped/boolean geometry and curved profiles are not reconstructed. Layered material names are retained; editable layer semantics are not fully rebuilt. Obtain real pilot exports and verify losses. |
| **FR-04 AI change workflow — P0** | Typed operations with explicit before/after preview: selected-scope type/specification edits and repetition, analysis, revision explanation, crew evaluation, and new concept layouts from a room program. Layout creation has a separate explicit footprint/level scope and shows its dimensions, areas, access, assumptions and complete creation set before acceptance. GPT-6.1 Sol is the default; existing legacy defaults upgrade without changing historical provenance. Repetition and layout previews include new IDs/hosts and source-state checks; acceptance rederives and validates the complete transaction before mutation. Layouts preserve a selected slab and never remove existing geometry; stale revisions, changed creation diffs, incompatible types and geometry locks are rejected. | `api`, `transactions`, `repetition`, `server-repetition`, `layout`, `layout-transactions` and `copilot-layout` suites cover no preview mutation, source locks, scope, stale/tampered diffs, child relationships, mixed-operation rejection and atomic acceptance. Native live-provider repetition preserved 43/v1 during preview, accepted 45/v2 and undid to 43/v3 in 0.2.0. In 0.3.0, live GPT-6.1 Sol produced the requested eight-room program from blank/selected-slab inputs. The production browser UI demonstrated zero source elements until acceptance, then 39 elements, undo to zero and redo to 39; native 0.3.0 also passed creation/accept/undo/redo and saved 39 elements/v4 after user-completed Keychain authorization. A review-table rendering defect found during native QA was fixed in 0.3.1 and checked in the rebuilt browser UI. See validation for build scope. | The proposed **80% correct-preview** target and **zero unapproved persistent edits** need task-based pilot measurement; a successful native task and unit tests cannot establish the former. |
| **FR-05 Documentation — P0** | Model-derived plans, section/elevation overviews, element annotations, full room/door/window schedules, quantities, PDF, CSV and XLSX. Rows retain IDs, version/unit metadata and visible missing specifications/classifications. Workbooks include Project, Quantities, Estimate, Rooms, Doors, Windows, Schedule and Assumptions sheets. | `drawings` and `model-schedules` suites construct PDF output and serialize/re-read a real workbook, check source metadata, current model values and formula-injection escaping. The 0.2.0 native checkpoint's 16-page v3 PDF visually passed all pages; its workbook parsed eight sheets and 8/7/10 room/door/window rows. | One fixture does not establish all future layouts. Production sheet/annotation authoring and fabrication detailing are not implied. Drawings need architect review. |
| **FR-06 Cost engine — P0** | Deterministic quantities, explicit material/labour/equipment rates, waste, independent allowances, calendar-day overhead and optional incremental crew costs. Unknowns stay unpriced. Explicit rate currency/source fields prevent silent currency conversion. Revision comparison separates geometry/type/rate changes and provisional subtotal deltas. | `engine`, `revisions` and `model-schedules` suites cover source formulas, waste/allowances, unknown costs, unit/currency changes, overflow guards, revised quantities and reproducible deltas. | Estimator confirmation of quantities, rate sources, exclusions, taxes and unmodelled work is required. Completeness measures entered scope; it cannot prove that all construction work has been entered. Demonstration inputs are illustrative. |
| **FR-07 Schedule engine — P0** | Editable activity networks, model/manual quantities, assembly/manual productivity, working weekdays, holiday exceptions, procurement releases, finite crew capacity and resource/dependency drivers. Assembly work days aggregate source quantity divided by its productivity. Extra crews enable concurrency rather than automatic per-task acceleration. | `engine` and `revisions` suites cover cycles, missing predecessors, resource demand, weekend/holiday dates, procurement, model updates, manual overrides and slower material substitutions. | Planner validation of templates, productivity, curing/inspection tasks, procurement and missing scope remains required. The current pool is generic crews, not a detailed trade/equipment logistics simulation. Dates remain preliminary. |
| **FR-08 Scenario optimiser — P0** | Bounded enumeration of approved type substitutions, crew availability, procurement and explicitly approved dependency-network variants. Sequencing approval is bound to the baseline activity IDs/categories/predecessors/source selectors; changing that network requires review again. Budget/deadline, locks, complete pricing, cycles and resources constrain candidates. Baseline, non-dominated alternatives and infeasibility reasons remain visible. | `engine` and `scenarios-sequence` tests check locks, incomplete pricing, objectives, Pareto trade-offs, unapproved/stale/cyclic/unknown variants, explicit predecessor diffs and a disclosed 128-combination limit. The final native package completed 24/24 demonstration scenarios in its worker and correctly blocked adoption of incompletely priced savings. | No arbitrary sequencing is invented. Planners must supply and approve alternatives with a rationale; resource feasibility does not establish construction-method safety. At most six stored variants and 128 combinations are searched, with truncation disclosed. Valid-alternative adoption still needs native planner acceptance; no global optimum is claimed. |
| **FR-09 Review collaboration — P1** | Real local accounts and per-project admin/editor/contributor/reviewer permissions; immutable published snapshots and server-bound comment authors. Portable review files contain a detached snapshot and matching comments; their viewer is read-only and does not change the open project. | `server-auth` tests exercise cross-project denials, roles and authorship. `review-package` tests cover detached data, comment scope, schema and checksum validation. Native v3 publish/export/reopen retained 43 elements and passed checksum validation in the 0.2.0 integration checkpoint. | Review files are plaintext exports with an integrity checksum, not encrypted or publisher-signed files. This provides local/file-based review, not synchronized remote collaboration. |
| **FR-10 Export/audit — P0** | PDF/workbook/CSV/decision JSON preserve version, units, source IDs, formulas, engine versions, rates, allowances, schedule assumptions, selected objective and scenario changes. Formal revision comparisons expose field and downstream calculation changes. Encrypted portable backups restore as a new revision while retaining current access decisions/history. | `drawings`, `model-schedules`, `revisions`, `storage` and `server-auth` suites cover metadata, real serialization, authenticated backups, tampering, restore and immutable snapshot conflicts. Native report evidence and final-package backup/revision comparison results are recorded in validation. | Agree the intended data-sharing/retention policy. Plain JSON, CSV, XLSX, PDF, IFC and review-copy exports contain project information; encrypted backups are a separate format. |

## Non-functional requirements

| PRD quality bar | Current implementation/evidence | Acceptance still required |
|---|---|---|
| **Correctness and reproducibility** | Deterministic measurement/cost/schedule/scenario/revision engines; versioned calculation rules, source IDs, finite-value guards and regression fixtures. | Architect/QS/planner-agreed independent tolerances and classified discrepancies on representative projects. |
| **Interoperability** | Explicit support boundaries, per-class reports, exporter round trips, malformed-input tests and pinned external fixtures with hashes. | A broader independent real-world IFC corpus and any requested buildingSMART/MVD certification; no such certification is claimed. |
| **Performance** | Measured 1,500/3,000-element synthetic engine/IFC timings, including sample counts and methodology in [VALIDATION.md](VALIDATION.md). | Agree real project-size limits and editing/rendering/interaction thresholds with pilots; test on their hardware. Engine timings are not a UI frame-rate or latency guarantee. |
| **Reliability and recovery** | Durable replacement, authenticated/capped recovery generations, encrypted portable backup, stale-write conflict handling, per-user drafts, save-before-close and corruption failures. Security records fail closed instead of rolling permissions/passwords backward. Final macOS restart and native new-project backup restore passed. | Native crash/migration checks, independent recovery drills and an operator-owned backup/key-loss procedure. |
| **Security and privacy** | Password-derived credentials, random sessions, project ACLs, encrypted records, OS-protected data/API keys, isolated renderer, loopback capability and denied external origins. Existing external env files are an explicit main-process-only option. Legacy plaintext Chromium cache is preserved in a verified encrypted archive before cleanup. | Independent security review and threat-model acceptance. Local HTTP is not TLS; this service must remain loopback-only. Project context is sent to OpenAI only for submitted requests; provider retention/privacy terms remain applicable. No enterprise SSO or hosted multi-tenant service is claimed. |
| **Explainability** | Source formulas, rate provenance, measurement/schedule issues, completeness, explicit assumptions and provisional-delta labels. | Test comprehension with architects, estimators and planners; confirm users do not interpret preliminary outputs as guaranteed prices or completion dates. |
| **Accessibility** | Keyboard shortcuts, native menus, labelled controls, element-list/table navigation and accessible review/error information. | Formal keyboard-only, screen-reader and contrast checks on packaged desktop targets. No accessibility certification is claimed. |
| **Observability and analytics (§13)** | Bounded/redacted local diagnostics, request/error counters and storage-integrity events. Ten allowlisted product events persist as encrypted aggregate counts; AI generation/review and scenario compute durations are bounded aggregates. No prompts, model content, user IDs or project IDs are retained in usage records. | Instrumentation supports local event counts and coarse durations, not independently measured authoring time, quantity discrepancies or firm retention. Counter events are client-reported diagnostics, not tamper-proof outcome evidence. Agree consent/measurement and collect the pilot metrics without exposing project data. |
| **Release operations** | Final macOS archive/ASAR/secret/license inspection, 14 packaged smoke checks, strict local ad-hoc signature verification and native workflow checks passed. CI source verification and macOS arm64/x64, Windows x64 and Linux x64 packaging all passed. Signed-feed update validation exists; updates remain disabled without a trusted publisher/feed. | Native acceptance on the other target platforms, Apple Developer ID/notarization, Windows signing and a publisher-operated trusted feed as applicable. An ad-hoc signature and passing package builds do not establish a signed public release. |

## External release and pilot gates

1. **Three to five design-partner firms** complete the PRD journey on representative low-rise work: create/import → review/accept/revert an AI edit → document → estimate → schedule → compare/export.
2. Independent reviewers agree measurement tolerances, validate cost/schedule inputs and check every reported trade-off against the supported scope. Numeric tolerances are not yet established; do not invent them.
3. Measure the proposed AI correctness, review/correction time and repeat-use goals. The PRD proposes at least two firms reusing the product; this is an outcome to observe, not a completed code check.
4. Extend the recorded macOS integration evidence to the complete agreed acceptance journey, recovery drills and each target OS. Supply publisher signing/notarization/feed credentials before claiming public signed distribution or automatic updates.
5. Independently review the approved sequencing alternatives and close or explicitly accept interoperability, accessibility and operational limitations. None of these records imply structural approval, code-compliance sign-off or a general-purpose CAD system.
